Lecture 3 复习：Debugging（调试）

主题：异常与 traceback · 避免 bug · 静态分析 · 最小失败样例 · 手动调试 · pdb 调试器 · AI 调试 讲师：Dr. Simon Warder

1. 为什么调试重要

  • 开发软件时，花在调试上的时间往往不少于写代码本身。
  • 调试是必须主动掌握、能大幅提升效率的技能。

历史上的著名 bug

事件 说明
世界上第一个 bug（1947） Grace Hopper 在日志里记录了一只真正的飞蛾卡在继电器里，普及了「debugging」一词
Y2K 千年虫 两位数年份导致 2000 年问题，全球花数十亿美元修复
达兰导弹（1991） Patriot 系统时钟 100 小时漂移 1/3 秒，导致拦截失败，28 名美军丧生

有趣的 bug 类型

类型 特点
Heisenbug（海森堡 bug） 一被观测/调试就改变或消失（借用量子力学「观察者效应」）
Bohrbug 在明确（但可能未知）条件下稳定复现的 bug
Mandelbug 极其复杂、几乎无法修复的 bug（借 Mandelbrot）
Schroedinbug 只有当你发现它「本就不该能工作」时才显现的 bug

2. Python traceback 与异常

读 traceback

traceback 是异常发生时给出的调用栈报告。从下往上读（最底下一行是异常发生的位置，但不一定是 bug 根源）。

NameError: name 'exp' is not defined
  • 第一行是异常类型；Traceback (most recent call last) 下面按调用顺序列出每一层。

常见异常（要能写出触发它们的代码）

异常 触发方式
ImportError from numpy import alalalala
ModuleNotFoundError import what
ZeroDivisionError 1 / 0
IndexError [1,2,3][100]
TypeError "hello" + None
SyntaxError 语法写错（如 2+2 =="4"）
IndentationError 缩进错误（for 下面没有缩进）
RecursionError def f(): return f() 无限递归

可自定义异常；异常类型完整列表见 Python 文档。

3. 避免 bug（写代码时就考虑）

  • 每个人都会写 bug，写代码时要为测试和调试而写。
  • KISS（Keep It Simple, Stupid）：能跑起来的最简单方案是什么？
  • DRY（Don't Repeat Yourself）：每块知识只应有单一、明确的权威表示（常量、算法等）。
  • 松耦合（Loose Coupling）：限制代码间的相互依赖。
  • 有意义的命名：变量/函数/模块用有意义的名字，别用晦涩的数学符号名。

4. 静态分析（Static Analysis）

  • 解释型语言（Python/Matlab/JS）vs 编译型（C/C++/Fortran）：编译型能在编译期发现缺 import、类型不匹配等 bug，Python 没有这一步。
  • Python 静态分析工具：
    • pyflakes：最简单，快；检测语法错误、缺 import、名字拼写错误。
    • flake8：pyflakes + pep8，额外检测 PEP8 风格违规。
    • pylint、pychecker。
    • 笔记本版本：flake8-nb。
  • 强烈建议在编辑器/IDE 里集成，能显著提升效率。

5. 调试工作流（Workflow）

没有银弹，但策略能帮忙。理想情况是把问题隔离到少量代码行，用短修改-运行-失败循环：

  1. 让它稳定失败：找一个每次都同样失败的测试用例。
  2. 分而治之：定位到某个模块 → 某个函数 → 某一行。
  3. 隔离出最小可复现失败样例（MFE）。
  4. 一次只改一件事，重跑失败用例。
  5. 用调试器理解到底哪里错了。
  6. 记笔记、保持耐心。
  7. 修好 bug 后，把这段代码加入测试套件，防止回归。

6. 最小失败样例（Minimum Failing Example, MFE）

  • 能复现某个 bug 的最简单代码。
  • 找人帮忙调试时，提供 MFE 是好习惯，能大幅缩短对方调试时间。
  • 给开源项目报 issue 时，开发者常会要求「Please could you provide an MFE」。
  • 例子：几百行的 Devito 代码，浓缩成十几行的 MFE 后不到一小时就定位并修复。

7. 手动调试

  • print 语句：在可疑处打印变量值，快速定位问题行。
x = some_function(inputs)
print(x.property1, x.property2)
  • IPython.embed()：在代码中途嵌入交互式解释器，检查当时状态。
x = some_function(inputs)
from IPython import embed; embed()

8. Python 调试器 pdb

能做什么

  • 查看源码；在调用栈上上下移动；查看/修改变量值；设置断点。

三种启动方式

  1. Postmortem（事后）：出错后（仅 IPython）%debug 进入调试器。
  2. 命令行：python -m pdb script.py。
  3. 代码内：在想要暂停处插入 breakpoint()（旧代码等价 import pdb; pdb.set_trace()）。

常用命令

命令 说明
l(list) 列出当前位置代码
p(print) 打印变量值（p a）
n(ext) 执行下一行（不进新函数）
s(tep) 执行下一条语句（进入新函数）
c(ontinue) 继续到下一个断点
b(reak) 设断点（b 34）
u(p) / d(own) 上/下移动调用栈
bt 打印调用栈
a 打印局部变量
!command 执行 Python 命令（区别于 pdb 命令）
q 退出
h / help 帮助

把 warning 变成异常

np.seterr(all='raise')   # 让 divide/invalid/over 等变成异常，便于 post-mortem 调试

pytest 里调试

  • pytest --pdb my_test.py：异常时 post-mortem。
  • pytest --pdb-failure：测试失败时用调试器检查。

图形化/替代工具

  • pudb（半图形化控制台调试器）、VS Code 调试模式、Mu 编辑器。

9. AI 与调试

  • AI（Copilot、Claude 等）是强大的编程/调试助手，但有限制：容易被误导、会幻觉、自己也会写出 bug。
  • 经验建议：
    • 花时间最久的一些 bug 恰恰是 AI 生成的——因为太急没仔细检查。
    • 你最终要为自己产出的所有代码负责。
    • 上下文很重要：网页聊天适合小片段，不适合大型代码库；agentic 工具（Claude Code/Codex）对大代码库更强，但 MSc 作业通常不允许用。
  • 学习建议：必须能自己从零写代码；AI 可用于辅助学习（澄清概念、优化建议），但依赖 AI 写/调代码长期对你不利。

10. 小结（今天学到了什么）

  • 每个人都会写 bug。
  • 调试工具能省大量时间和精力。
  • 静态分析工具能避免很多简单 bug。
  • 用 IPython.embed() 手动调试。
  • Python 调试器 pdb 的基础用法。
